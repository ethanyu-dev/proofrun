## 为什么调用文本模型更多

9 次文本模型调用分别由 4 次 REPLAN、2 次 VERIFY、1 次定期检查和 2 次返回相同状态触发。当前 `JevDecisionModel` 的 review 调用通用 `ChatModel.decide`，只返回一个下一步动作；没有输出可持续执行的阶段计划，也没有锁定下一阶段或记录结构化完成条件。因此检查后很快又回到同一个全局动作选择问题，出现开关弹窗循环。

其中 #22 耗时 74.022 秒，记录含 617 个 reasoning token，最终只返回一次点击。可确认是端到端模型调用长尾，但记录不能继续拆分供应商排队、网络和推理时间，也不能把它完全归因于上下文长度。其余文本调用也累计 164.435 秒；问题并非只有这一个慢请求。

JEV 输入为 385,754 token，9 次文本模型输入为 214,045 token；总量约为纯 LLM 的 7.47 倍。后期每次文本审查包含最多 8 个历史状态，文本上下文达到约 6.3 万字符。历史增长是成本与延迟风险，本次没有独立对照实验可量化其因果贡献。

## 比较口径存在缺口

objective 写了五步，acceptanceCriteria 却只有一项“搜索表单下拉包含两个选项”。纯 LLM 的最终报告明确按这一项结束，没有打开新增弹窗。JEV 做了一部分弹窗操作，最后也只按这一项报告通过。

所以两组 PASSED 只说明唯一结构化验收项通过，不等于完整五步均验收；本次执行总耗时不是同等工作量下的模型速度对照。

## 优先优化方向

1. 先统一完成条件：把搜索下拉、弹窗下拉、两种默认开关、关闭且不提交分别记录为阶段和验收项。LLM/JEV 共用完成门槛，不能通过减少任务覆盖来优化速度。
2. JEV 按当前阶段选动作：限定搜索区或当前弹窗，为同名“白名单类型”附带容器身份；未完成当前范围取证时不能任意跳至新增弹窗。变化优先在阶段内排序。
3. 页面就绪与进展检查由执行器提供：初次没有业务区控件时有界等待/重采集，避免点击无关导航；阶段、区域、展开状态和证据共同判断进展，识别 A→B→A 循环。
4. 将 LLM 审查结果升级为可执行的阶段目标、允许动作和结束条件；阶段切换、确实缺少目标或连续恢复失败再审查。保留最终证据判定，不能简单删掉安全/正确性检查。
5. 输入使用阶段证据摘要与当前控件，减少重复历史；分开记录供应商、浏览器、取证及编排时间。在相同完整验收、相同模型配置下多次重跑，再比较中位数和长尾。
