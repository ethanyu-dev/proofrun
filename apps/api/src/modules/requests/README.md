# 请求读取与摘要

请求和冻结成员关系保留在 `pr_verification_requests`、`pr_verification_request_cases`；新的单 LLM 运行只写 cases 一份关联。`pr_request_runs` 视图以 cases 为主运行来源，并补入历史 `pr_verification_request_arms` 的从运行；复用历史双跑时只冻结额外的从运行，不重复写主运行。历史表和原始报告保留，任务仍是执行与报告的事实来源。`projector.ts` 供详情和摘要刷新共用，继续调用 Contracts 的 `summarizeReport`、`summarizeRequestCase`、`summarizeRequest`，不在 SQL 复制判定规则。

`pr_request_summaries` 保存列表需要的计数和状态；索引列从同一 JSON 生成，不能独立更新。列表通过执行状态、报告状态、创建时间和请求身份筛选分页，不再分批读取历史任务并在应用层筛选。详情保持直接读取原始事实；公开响应结构及计数口径不变。

## 一致性与恢复

- 任务的状态、报告或定义改变，以及请求成员/执行组变化，会在同一业务事务中写入 `pr_request_summary_dirty`。共享任务会标记全部关联请求；心跳、期限、步骤中间进度及模型用量等不影响列表摘要的更新不触发重算。
- 列表在可重复读事务内锁定失效标记、重算并清除标记，然后分页。刷新与读取使用同一快照；竞争写入改变标记行版本时，由数据库事务封装重试。不能使用 `SKIP LOCKED` 跳过失效摘要，也不能将刷新失败降级为返回旧计数。
- 每批最多加载 100 个请求，保留完整成员。普通列表刷新当前快照内全部失效项，所以大量新任务或集中完成后的首次读取仍有增量刷新成本；这不是后台最终一致缓存。
- 首次迁移和重启准入前，按每批 100 个请求、独立事务完成待处理摘要。已提交批次不重做，中断后继续剩余标记；历史规模影响首次升级启动时间。
- 全量重建使用 `pnpm maintenance:api --request-summaries --apply`，沿用维护入口独占数据库的约定，先停止 API。省略 `--apply` 查看请求数量。重建只更新派生数据，不修改任务、报告、成员或证据。将来变更汇总算法或新增摘要依赖字段时，必须同步触发范围并在迁移中标记历史请求重建。

## 搜索与分页

搜索仍按请求身份、标题、Case 身份、Case 主任务目标做大小写不敏感的字面子串匹配。摘要保存各字段及其拼接文本；`pg_trgm` 的 GIN 索引用于粗筛，独立字段匹配用于消除跨字段拼接假命中。短词或过于常见的查询可能仍需扫描，不能承诺所有模糊搜索都是固定成本。迁移需要数据库支持并允许创建 `pg_trgm` 扩展，可由管理员预先安装。

游标绑定搜索和状态筛选，保留 PostgreSQL 微秒时间，以 `(created_at, request_id)` 排序；摘要刷新从原表复制时间，不经过 JavaScript 毫秒时间往返。单次响应保证快照一致，连续 HTTP 翻页期间的状态变化不会被冻结。

一致性回归与独立数据库压测入口见 [测试说明](../../../../../tests/README.md)。
