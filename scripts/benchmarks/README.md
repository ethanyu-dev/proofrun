# Browser Node 容量基准

`node_capacity.py` 在 Linux 节点上测量独立 profile 数量与 profile 内分组并发。仅依赖 Python 3.10+ 标准库和已安装的 ProofRun Browser Node、Chrome、用户 systemd。

## 运行

使用原节点运行用户，不要 sudo。先停止提交新任务，确保 Console 中节点无活动会话：

```bash
python3 node_capacity.py --mode smoke
python3 node_capacity.py --mode matrix --repeat 2
```

默认矩阵先以 1 个 profile 测分组并发 1、2、4、6、8，再以分组并发 2 测 profile 数量 2、4、8、12、16。每个 profile 固定完成 6 个独立分组；每组包含导航、填写、点击和三次真实 DOM/截图采集，两次模拟模型等待各 3 秒。可调整：

```bash
# 固定分组并发，对比节点容量；每个点重复 3 次。
python3 node_capacity.py --mode capacity --profiles 4 8 12 16 --concurrency 2 --repeat 3

# 固定 1 个 profile，对比分组并发。
python3 node_capacity.py --mode profile --groups 8 --concurrency 2 4 6 8 --repeat 3

# 去掉模型等待，测浏览器密集操作压力；应单独分析，不能混入 3 秒等待曲线。
python3 node_capacity.py --mode capacity --profiles 1 2 4 8 12 16 --concurrency 2 --think 0 --repeat 2
```

已完成分组的 tab 当前保留到整个 profile 结束，因此内存随分组总数增长，不能只按同时运行的组数估算。

`--groups` 控制每个 profile 的总分组数量，`--think` 控制每次模拟模型等待秒数。`--output` 必须指定尚不存在的目录。配置采用默认 `~/.config/proofrun/node.toml`；Python 3.10 支持标准单行路径字符串，自定义 TOML 写法可改用 Python 3.11。

## 测量范围

包含真实发布二进制的 stdio 命令入口、SQLite、systemd/cgroup 会话、agent-browser、Chromium、tab 切换、DOM 观察与截图写入。每个 profile 内浏览器命令串行，模拟模型等待在锁外发生，与当前分组执行的主要排队关系一致。检查填写和点击结果的 tab 归属及会话最终 CLOSED。

不包含生产 API 调度、Railway worker 数量、远程证据上传、真实模型请求及限流、业务站点脚本/网络负载或生产身份状态。因此只能据此选出特定工作负载的候选容量，不能宣称获得所有线上任务的全局最优值。页面为 200 行表格和输入交互的本机夹具，重型应用需要另做代表性验收。多语言页面的共享 Cookie 等业务干扰也不属于此性能基准。

## 隔离与停止

- 读取原节点配置中的路径及会话数量，不读取凭据或登录快照。
- 每档启动独立数据目录、节点身份、systemd 会话和浏览器 profile，只访问本机随机端口页面，不连接生产控制面，不修改生产 capacity。
- 每秒检查物理内存及原节点账本。低于 3 GiB 或总内存 20% 的较大值，或生产出现未关闭会话，即停止继续派发并回收测试会话；在途命令有超时。这不是绝对的瞬时峰值内存保护，因此应在空闲节点逐档测试。
- 同一用户的测试使用独占锁；Ctrl+C / SIGTERM 停止继续派发并执行正常回收。
- 命令、正确性或关闭检查出现任何错误，停止后续档位。正常结束通过正式节点 shutdown 清理；独立会话同时有短租约保护。
- 成功档位清除本次产生的截图/profile，只保留结果、账本和日志；失败档位保留现场。原节点服务始终不被重启或停止。

## 结果

默认保存在 `~/proofrun-benchmark-日期时间/`：

- `environment.json`：二进制版本、机器信息与测试参数。
- `results.jsonl`：每档吞吐、耗时、命令及锁等待 P95、整机 CPU、可用内存和错误。
- `p*-g*-r*/metrics.json`：每秒资源采样。
- `p*-g*-r*/node.log`、`state/node.db`：诊断与会话关闭依据。

比较相同 groups/think 参数、同一硬件下的重复试验。优先选择无错误、关闭均核实、内存留有余量且吞吐提升开始放缓之前的档位；同时检查尾延迟。所有 CPU/内存指标为整机测量，存在其它服务负载时不应将差异全部归因于浏览器。容量不是 worker 数；一个 worker 当前一次仅执行一个任务，部署的 worker 数量和模型配额也需满足所选总并发。

## 单任务延迟参考

2026-10-13，Ubuntu 22.04、8 vCPU、15224 MiB 内存、无 swap，节点版本 `node-v0.1.0-alpha.8`、引擎 `0.38.1`。下列每档重复两次，均使用每组两次 3 秒模拟模型等待；耗时为 `profileP95Seconds` 的两轮均值，包含会话创建与业务操作，不包含会话关闭。单 profile 下该指标就是该 profile 的业务耗时。

| 同时运行 profile 数 | 每个 profile 总组数 | 分组并发 | profile 业务耗时 | 整机平均 CPU | 最低可用内存 |
| ------------------- | ------------------- | -------- | ---------------- | ------------ | ------------ |
| 1                   | 5                   | 2        | 20.74 秒         | 3.93%        | 13886 MiB    |
| 1                   | 5                   | 5        | 8.44 秒          | 8.96%        | 13880 MiB    |
| 1                   | 8                   | 4        | 15.62 秒         | 7.28%        | 13810 MiB    |
| 1                   | 8                   | 8        | 9.30 秒          | 10.74%       | 13791 MiB    |
| 12                  | 8                   | 8        | P95 19.63 秒     | 87.66%       | 9005 MiB     |

这组夹具支持把单任务默认分组并发提高到最多 8：5 组任务耗时缩短约 59%，8 组任务相对并发 4 缩短约 40%。12 个 profile 同时满载时 CPU 已接近瓶颈，命令排队 P95 约 4.7 秒，不应据此继续提高节点容量。真实模型配额、重型页面和远程网络未纳入测量，上述比例不是线上任务加速保证。

## Agent Loop 基础基准

```sh
pnpm benchmark:agent
pnpm test:benchmark
pnpm dev:console
# 打开 Console 的 Benchmark 导航，或访问 /#/benchmarks。
```

`benchmark:agent` 构建当前源码后运行完整的 `agent-loop-basic-v1` 套件，不需要模型密钥、数据库或浏览器。开发态看板选择“脚本协议回归”后运行；已连接的生产 Console 可切换线上调度，也可在本地归档视图导入 CI 下载的 JSON。开发接口只在回环同源访问时开放，固定执行命令，不接受任意命令或目录。默认读取最近 20 个归档，基础套件单次读取及导入上限 20 MiB，V2 完整任务归档上限 64 MiB；更早结果手动导入。

| 场景               | 固定预期                         | 最大轮数 |
| ------------------ | -------------------------------- | -------- |
| 表单填写与单次提交 | 保存 Alice、只提交一次、完成结算 | 3        |
| 只读观察与证据结算 | 初始导航后不派发写动作           | 1        |
| 无效目标拒绝与恢复 | 非法目标不派发、反馈后恢复提交   | 4        |
| 未知副作用停止重试 | 提交一次后停止，不误报通过       | 2        |
| 长页面上下文裁剪   | 长正文压缩后仍保留约束并完成循环 | 3        |

每个场景使用真实 `execute`、上下文投影、提示词/工具装配和 `ChatModel` HTTP 适配器；回复、页面、租约和证据交付使用夹具。它验证循环协议，不代表真实模型成功率、浏览器操作正确性、生产性能或费用。额外的浏览器及业务测评可分别运行 `pnpm test:agent:browser` 和 `pnpm eval:e2e`，依赖见 [测试说明](../../tests/README.md)。

所有轮次必须包含七模块、完整请求回执及单工具回复，正文不得超过 12,000 字符。归档写入 `.proofrun/benchmarks/<时间>-<运行 ID>.json`，包括源码身份、配置、检查、逐轮请求/回复和实际派发回执。失败照常落盘并以非零码退出；缺少 Git 元数据的构建明确标记 `unversioned` 或环境提供的提交，并标记工作区未核验。产物属于运行结果，不提交到仓库。

看板分开显示 `task/state/page/history/evidence/budget/feedback` 的字符占比、系统指令与工具定义长度，保留 JSON 结构开销及原文。页面另外拆分正文、控件、网络及运行时/缓存，并显示当前视图；截图单独计数，不折算字符或 token。模型提出的工具与真正派发的命令独立展示；首轮前导航与观察归入轮次 0。这里的字符数是 UTF-16 文本长度，不是 token；夹具提供的 token 不进入费用统计。

显式基线比较：

```sh
pnpm benchmark:agent --baseline /absolute/path/to/passed-run.json
```

仅接受相同套件、模型预算和场景集合的通过归档。每个场景轮数不得增加，正文峰值最多增加 10%；不兼容也会失败并保存结果。看板选基线用于查看差值，不会重写归档中的门禁结果。耗时只用于本机诊断，不设跨机器性能门限。修改场景或固定门限时必须升级套件版本。

## 真实模型与本地浏览器发布检查

```sh
pnpm benchmark:setup
pnpm benchmark:release --version v0.1.0 --env-file .proofrun/local.env
pnpm benchmark:gate
```

需要本机 Chrome、Rust 工具链和真实模型的 `PROOFRUN_MODEL_BASE_URL`、`PROOFRUN_MODEL_API_KEY`、`PROOFRUN_MODEL`。只有显式指定 `--env-file` 才加载文件内的模型/浏览器白名单字段，已有进程环境优先；服务地址仅保存摘要，密钥不会进入归档。可选的 vision、token 参数、thinking、reasoning effort 和输出上限复用 Agent 配置。浏览器使用独立临时 profile，不操作用户已打开的窗口。`benchmark:setup` 从固定版本 npm 包准备本机原生引擎，不安装 Chrome；路径可通过 `PROOFRUN_AGENT_BROWSER_BIN`、`PROOFRUN_CHROME_BIN`、`PROOFRUN_TEST_BINARY` 指定。

`benchmark:real` 构建并调用正式执行器、正式 ChatModel 和原生 session-host，真正访问本机 HTTP 页面；`benchmark:release` 还原子写入 `.benchmark-release/real.json` 发布候选。运行开始即废弃旧候选，未完成或失败的候选不能通过门禁。每例最多 12 次模型调用、10 次浏览器动作、180 秒，总计最多 144 次真实模型调用；不自动重跑以筛选成功结果。

`agent-loop-real-v4` 固定覆盖以下十二例，旧 v1 / v2 / v3 归档仅供复盘，不能满足当前发布门禁：

| 场景           | 独立判定                                                          |
| -------------- | ----------------------------------------------------------------- |
| 表单填写与提交 | 服务端实际收到一次 Alice / Hangzhou，模型证据结算通过             |
| 只读核验       | 真实页面状态核验通过，没有写入或额外动作                          |
| 旧观察恢复     | 刷新真实观察使旧目标失效，宿主拒绝、模型收到反馈并恢复完成        |
| 丢回执保护     | 真实提交后注入 UNKNOWN，实际只写一次，不能误报业务通过            |
| 长页面裁剪     | 真实长页面触发文本裁剪，仍在 12,000 字符预算内完成提交            |
| 选择控件       | 原生下拉框和复选框生成一次正确写入，交付正文与证据齐全            |
| 跨标签读取     | 实际打开详情、读取两个编号、切回主标签，保留两页且没有写入        |
| 展开阅读       | 实际展开两项内容、读取编号和价格、交付完整对比且没有写入          |
| 网络与缓存分页 | 实际响应头正确，精简视图不带 DOM/截图，分页交付全部 24 个缓存条目 |
| 网络后返回页面 | 网络详情核验后恢复同一快照，再实际点击并读取 RETURN-73            |
| 表单校验与修正 | 先观察缺少城市的提示，再补填提交，服务端恰好记录一次正确写入      |
| 空查询恢复     | 先观察无匹配结果，再替换查询并交付正确编号与库存，业务写入为零    |

五项通用浏览器场景使用 `taskKind: browser` 与空验收数组，由 `browserResult`、实际观察及服务端事实独立判断，不能靠空验收通过混过门禁。线上基础套件为独立的七场景 `agent-loop-deployed-v2`，包含原五例和表单校验、空查询恢复两例；本地/CI 的十二例还覆盖跨标签、展开和网络 context。线上结果是部署后验证，不能替代本地/CI 发布证明。迁移 047 冻结每次线上运行的套件版本，旧五场景按原版本结算。

旧观察和丢回执为明确的故障注入，不代表自然故障率。控制面租约、调度和证据发布在进程内适配；真实模型、HTTP 页面、浏览器 DOM/截图及写入都实际执行。该套件不覆盖生产控制面、登录、远程节点和 Linux cgroup 监管。DOM 与截图保存在 `.proofrun/benchmarks/<运行 ID>/<场景>/`，JSON 保留每轮请求/回复、供应商 token、模块分布、实际派发及原始回执、故障标识和服务端写入事实。

Console 默认“真实模型 + Chrome”，填写发布版本后点击“运行真实基准”会执行发布套件；版本留空则记录为开发运行，不能作为发布候选；开发服务可显式读取固定的 `.proofrun/local.env`，网页不能传入任意参数。只有完成的归档进入列表，运行过程和失败显示在日志中。真实/脚本结果分别标记；脚本通过只表示协议回归通过。可选 `--baseline /path/to/real.json` 要求同套件、模型选项、浏览器版本和通过基线，轮数不增加、上下文峰值最多增加 10%。

发布端 `benchmark:gate` 拒绝脚本、缺例、不完整、失败、超过 24 小时以及源码指纹不匹配的报告。源码指纹包含源文件、提示词、测试、工作流与依赖锁；编辑后必须重跑。报告是受信任的本地/CI 产物，不是数字签名证明，外部导入只用于查看。

CI 主分支和手动运行调用 `.github/workflows/real-agent-benchmark.yml`。仓库需设置三个同名模型 secrets；模型其它选项使用同名 repository variables。凭据缺失直接失败，不回退脚本。PR 不调用带密钥的模型，只执行脚本及编译检查。Browser Node release 同时依赖脚本与真实套件成功。

API、Agent、Web 最终 Docker 镜像在 `verified` 阶段校验 `.benchmark-release/real.json`；CI 仅从同一次工作流下载通过的真实报告。本地需先执行真实套件，再构建镜像；源码变动或报告过期应先重跑，不复用旧的构建缓存作为新的发布证明。Railway 等远端构建也必须通过受控 CI 将当前报告带入构建上下文，直接从 Git 构建且无报告会被拒绝。模型密钥、浏览器配置和证据目录不进入镜像。`--target build` 仅用于无密钥 PR 的编译检查，不产出可部署的最终服务镜像。

### V2 真实任务

看板新增「基础验证 / V2 真实任务」页签，分别筛选运行与版本；V2 可使用 `pnpm benchmark:v2 --env-file .proofrun/local.env` 或本地看板发起。V2 使用固定历史任务：接口邀请活动五语言访客验证（14 步）与 Novita 官网导航、网络及页面验证（9 步）。来源任务 ID、原定义摘要、历史结论、实际冻结定义、逐步结果和逐轮 context / 工具原文一并归档。全部使用真实模型、独立 Chrome 与生产站点，没有脚本模型回复。

历史定义保存于 `contracts/fixtures/benchmark-v2/`，保留完整步骤、验收标准、分组和原预算；运行时仅生成新任务身份、移除已退役的 resourceKey，并固定空白访客环境和禁用人工介入。真实宿主回执证明访客身份，网络和运行时证据来自实际采集。V2 正文沿用 Agent 默认 64000 字符上限，基础套件的 12000 字符及其他门限不变。V2 保留正式执行器已有的最多四项纯网络读取批次，不能携带进度写入；基础发布套件仍严格每轮单工具。完整任务与网络原文归档上限为 64 MiB，不影响执行预算。页面发生变化、环境缺失或任一步未完成都如实失败，不追加重跑抽选通过结果。

V2 可在本地执行，也可在已连接的生产 Console 中选择「线上调度与存储」，通过「开始 V2 测试」发起固定双任务。线上使用独立套件 `agent-loop-v2-deployed-v1`，后台复用正式调度器与 Agent，按版本保存来源、完整步骤、逐轮 context、工具回执和实际 API / Agent / Node 身份；离开页面不停止运行。两类套件共用单个活动运行围栏，切换页签会提示正在运行的测试集。未知创建回执重试复用 UUID；结束后可重新创建完整一轮，失败归档保留。

只有「基础验证」的本地/CI 完整十二场景参与发布门禁，必须全部通过。V2 线上及本地运行仅用于诊断，失败、未运行或历史能力缺口均不阻塞发布，也不能替代基础套件；24 小时有效期、源码指纹、单例预算和证据要求不变。运行中的生产任务仍需按部署流程安全收尾，不为绕过活动任务检查而强制中断。多分组的工具回执按调用 ID 与步骤归属，避免同一轮号串入其他分组。V2 同样不发送飞书通知，包括新运行及旧通知队列的重试、更新；普通业务通知保持原行为。

## 按需 context 与网络基础检查

首次观察使用页面视图。网络查询后，下一轮只提供当前网络结果、页面身份、文档语言、覆盖边界与任务/进度/操作账本；正文、控件、截图及历史正文不重复发送。`context_read(section=page, observationId)` 恢复同一快照的页面视图和已验证截图，不发浏览器命令、不重置网络选择；实际重新观察后旧选择失效。精简视图不开放浏览器动作，执行端也拒绝跳过恢复的动作。

运行时列表默认摘要化，Cache Storage 条目默认不展开，其它列表保留少量样本。`runtimeLists` 区分原始采集完整性与当前省略量，`context_read(section=runtime, path, offset)` 每页最多交付 20 个完整条目。主动详情超出固定 context 预算时明确失败，不静默截断成完整证据。`state.contextReads` 保留已读页偏移、返回数量和实际缓存状态计数；翻页使用主动详情的 `nextOffset`。重复同页或交替旧视图受无进展保护，采集范围说明不作为普通列表裁剪。原始观察与 DOM/NETWORK/RUNTIME 归档保留不变；视图读取消耗原模型轮次，不能追加时间或动作预算。

`tests/agent/network-view.test.mjs` 覆盖同快照恢复、截图隔离、过期身份/非法路径、分页与预算边界，使用协议夹具，不代替真实基准。v3 的两项网络场景实际使用模型、本地 Chrome、HTTP 请求和 Cache Storage；仍不覆盖生产站点、线上调度和远程节点。

## 发布版本与线上运行

归档 v2 的主维度是 `release.version`，每次运行还有独立 `id`，同一版本可以保留多次成功或失败。`release` 同时记录 `buildId`、完整 `commit`、`sourceFingerprint` 和 `kind`。commit 用于追溯源码，源码指纹覆盖未提交变更；不能只用同一 commit 判断运行条件相同。历史 v1 可查看但归为“历史未标版本”，不能通过新发布门禁。

本地用 `--version v0.1.0` 或 `PROOFRUN_RELEASE_VERSION` 指定版本；`benchmark:release` 必填，普通本地运行留空生成 `dev-<源码指纹>`。`PROOFRUN_BUILD_ID` 可指定构建身份，默认本地源码指纹或 CI 的 run ID + attempt。CI 自动检查使用 `ci-<完整 SHA>`；手动真实基准工作流的 `release_version`、Browser Node 发布的 `version` 会传入报告。正式服务发布应在真实基准工作流显式指定同一发布版本，并使用该次工作流生成的报告构建三个镜像。

最终镜像在门禁成功后生成 `build-info.json`，API 和 Agent 从各自编译产物旁读取它。运行时变量和网页不能覆盖清单；缺失时明确显示 development，禁止发起线上基准。API、Agent 的版本和源码指纹必须匹配这次入队身份，Node 记录独立发布版本及 sourceCommit；滚动发布导致的组件漂移会失败并展示实际值。

线上 API 配置 `PROOFRUN_BENCHMARK_NODE_POOL` 和 `PROOFRUN_BENCHMARK_ENVIRONMENT`，节点池需有可用的已配对 Browser Node，并能访问 `PROOFRUN_PUBLIC_URL`。Console 连接管理员后选择“线上调度与存储”，直接发起 `agent-loop-deployed-v2`。请求只提交幂等 UUID，固定七个合成任务进入原有持久队列，实际 Agent 调用已配置模型，实际远程 Node 执行独立访客会话。旧 worker 不领取新基准；API 与 Agent 都需升级。

同一控制面最多有一个活动套件，每例 3 分钟、12 轮、10 次动作、12000 字符，套件最迟 10 分钟结算；离开页面不影响执行，服务重启继续对账，丢失的在途运行按原监督器失败收尾，不重放写入。合成页面只在任务执行期开放，独立数据库账本核验访问/写入。每轮 context、模型原文、工具派发与故障、关闭状态以及各组件版本进入数据库，终态归档冻结。列表按版本过滤、每页 20 次运行，版本下拉显示最近 200 个版本；API 仍可查询更早指定版本。

线上套件测量部署链路，本地真实套件测量隔离发布候选，两者独立比较，不能互相冒充通过。线上归档用于部署后验收；构建前的本地/CI 真实门禁仍然保留。生产接入需要部署新镜像并配置节点池；代码测试与模拟节点回归不等于线上验收完成。

### 执行与历史能力预检记录

新任务不再根据关键词静态判断工具能力，不自动跳过含 canonical、响应正文或私网图片要求的步骤。全部原始步骤、验收标准和预算交给正常执行流程；实际取证失败按已有执行协议记录原因和未完成结果，不能当作通过。模型配置、节点准入、环境准备和发布门禁校验保持不变。

旧归档中的能力预检和跳过记录仍可查看，仅代表当时的执行结果。`--preflight-only` 静态能力预检入口已移除。

看板分别显示开发回归结果和发布资格。未指定版本的运行即使全部场景通过，也只是开发回归；填写发布版本重新运行后才能成为发布候选。归档条件满足后，实际发布端仍检查当前源码指纹与 24 小时有效期。
